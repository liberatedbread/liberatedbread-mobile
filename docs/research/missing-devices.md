# Missing Devices — September 2026 Survey

**Survey date: 2026-09-23.** Every candidate below was checked against the
catalogue as it stood that day: 203 validated specs in `device-specs/devices/`,
about 270 unvalidated write-ups in `research-notes/`, 69 target stubs in
`targets/`, and the drafts in `new_devices/`.

!!! warning "A dated survey, not a live view"

    Like [Candidate Devices & Hardware Sourcing](device-candidates.md), this page
    is a snapshot. Specs land every week. Before starting on anything here, grep
    `device-specs/devices/`, `research-notes/` and `targets/` for it. Vendor
    status moves too: a shutdown date given here can slip, get reversed (Anova
    did exactly that), or arrive early.

This page answers one question: **which locally-controllable devices does the
catalogue still lack, and which of them should be written up next?** It follows
the older [candidates survey](device-candidates.md), which was checked against
69 specs. Much of that list has since been done, and it was organised around seven
technical tiers plus watch lists rather than a sweep of every device category. This survey starts again from the full catalogue.

## How the list was built

1. **Sweep.** Eleven independent searches, one per angle: orphaned and bricked
   hardware, subscription-gated hardware, lighting and hubs, climate and outdoor,
   energy, security, AV, health and wearables, kitchen/maker/robots, mobility,
   and network gear. One more angle mined the device lists of the open-source
   local-control ecosystems (Home Assistant local integrations, Theengs,
   Gadgetbridge, openHAB, Homebridge) for devices whose protocol lives only in
   that code.
2. **Coverage check.** Every candidate was grepped against the repo. Anything a
   validated spec already covers was dropped, including devices covered by
   family and platform specs (`tuya-generic-device`, `xiaomi-miio`,
   `bthome-v2`, `ftms-fitness-machine-service`, `govee-rgbic-light`'s LAN API,
   and so on). Candidates with only a research note were kept and marked.
3. **Adversarial fact-check.** Each candidate was checked on the web against
   its cited sources: do they exist, and do they describe *this* device's
   protocol? Vendor-status claims (shutdowns, bankruptcies, subscriptions) need
   a source. Claims resting only on a community project's README say so.
   Two premises failed outright and are left out: Spinn and Scout Alarm are
   still trading.
4. **Completeness passes.** Two critic rounds asked what was still missing. A
   final targeted pass covered well-known names the sweep had skipped
   (Anova, iGrill, Shelly, and the cloud-only orphans in
   [Parked](#parked-no-local-path)).

The result: **242 devices and families the catalogue does not cover**. That is
157 ready to spec from public work, 36 research targets, 30 already
documented well elsewhere (link them), 14 with no local path, 4 waiting on a
Bluetooth Classic value in the schema, and 1 held back on safety grounds. The 25 research notes worth graduating are listed
[at the end](#already-half-written-graduate-these-research-notes).

No prices this time. The older page's eBay snapshots are still the best
starting point for hardware cost.

## Reading the tables

- **Risk** uses the older page's
  [A / B / C vendor-risk classes](device-candidates.md#vendor-risk-classification-a-b-c).
  **A**: already abandoned, bricked or subscription-gated. **B**: likely to
  become A. **C**: a healthy vendor, where the value is local-first
  independence.
- **P1–P5** is priority against the repo's
  [three filters](device-candidates.md#what-this-repo-should-actually-spend-effort-on).
  P5 usually means an A/B device with a genuine local path that the phone
  reaches directly, whose protocol lives only in client code. A C device whose
  vendor gates local use behind a cloud login (EcoFlow) can also rate P5. P1 is a nicety.
- **Effort**: S is one sitting from public sources. M needs real
  consolidation or a capture. L is a large message catalogue, encryption, or
  several protocol generations.
- **Local path** ends with *phone-direct* when the phone talks to the device's
  own radio or LAN endpoint, the same path the vendor app uses. *Needs a
  host/bridge* means a LAN server, a plug-in dongle or an always-on listener,
  not a soldered ESP32: anything that needs soldering was scored down or parked.
  **Protocol** is the state of the public write-up: `code-only` (lives in a
  client's source; the most valuable to spec), `community-documented`,
  `vendor-documented` or `undocumented`.
- **Research target** means a local path is likely, but the public RE is too
  thin to draft a spec without captures. **July list** marks a device that was
  already on the older candidates page and still has no spec.

## Do these next

The 27 that best fit the project: every one is a spec-ready P5, or an
orphaned (A) P4 with a local path and enough public work to draft from. They
are ordered by priority, then risk, then effort. Most are
phone-direct. The exceptions say what else is needed: a LAN listener for
JuiceBox, and a plug-in OBD dongle for the Nissan Leaf.

1. **Instant Pot Smart Bluetooth (IP-Smart 6 qt)** — [A] · effort S. The official Instant Pot Smart Bluetooth app has been withdrawn and the vendor went through Chapter 11, so nothing official can drive these cookers. The phone-direct protocol is simple: BLE GATT services 0xDAB0 for control, 0xDAB2 for telemetry, 0xDAA0 for time and 0xDAC0 for recipes, with 20-byte frames. It is written down in a single README of a 0-star repo, so a validated spec is what keeps it alive, and it fits the Flutter app with no extra hardware. Commands start pressure cooking remotely, so require attended use. Sources: [openpot replacement app README](https://github.com/lizardlab/openpot)

2. **AM43 / A-OK / Zemismart BLE blind motors (Blind Engine)** — [A] · effort S · *July list*. The Blind Engine app is no longer on Google Play, so AM43, A-OK and Zemismart motors depend on third-party code, and homebridge-am43-blinds has been archived since September 2025. The phone talks straight to the motor's BLE GATT service with no hub or cloud: framed commands move, stop and set position, and notifications return battery, position and light level. No source describes the frame format in prose, so the spec is the missing piece. Exclude Tuya AM43 variants, note the one-client limit, and establish whether travel limits can be set over BLE. Sources: [A-OK AM43 Python BLE control](https://github.com/TheBazeman/A-OK-AM43-Blinds-Drive/blob/master/AOK-AM43.py) · [buxtronix AM43 ESP32 library](https://github.com/buxtronix/am43)

3. **Enel X JuiceBox EV charger (JuiceBox 32/40/48)** — [A] · effort M. Enel X Way North America shut down on 2024-10-11, leaving JuiceBox owners unable to change settings such as charge current. The charger sends UDP telemetry (ports 8042/8043/8047) to a configurable server, and owners can re-point that target over the telnet console on port 2000, through a DNS override or by masquerading the traffic. A LAN host, including a phone, can then read telemetry and set the current. The protocol lives only in juicepassproxy's code and a thin wiki. The spec must cap current at the wiring maximum and describe the Nov 2024 encrypted-UDP split. Sources: [JuiceboxRescueWiki: how communication works](https://github.com/JuiceRescue/JuiceboxRescueWiki/wiki/How-the-communication-Works-(Basic-info)) · [JuiceboxRescueWiki: console commands](https://github.com/JuiceRescue/JuiceboxRescueWiki/wiki/Juicebox-Console-Commands)

4. **VanMoof S3 / X3 e-bike (plus legacy S2/X2 and earlier)** — [A] · effort M. VanMoof went bankrupt in July 2023 and was bought by Lavoie, but every S3/X3 still depends on a per-bike encryption key and user key ID that only the vendor's account API ever issued. With the key exported once, the phone controls lock, lights, bell, assist levels, alarm and battery over local BLE with no cloud. The protocol exists only in client code (VanMoofKit, pymoof). A written spec plus an offline-key workflow keeps the bikes usable. Whether the API still serves keys is unknown, and the spec must leave out speed-limit and region changes. Sources: [VanMoofKit Swift client and exporter](https://github.com/SvenTiigi/VanMoofKit) · [pymoof Python BLE client](https://github.com/quantsini/pymoof)

5. **Sengled Wi-Fi smart bulbs** — [A] · effort M. Sengled's cloud has failed repeatedly since June 2025 and Amazon removed the Alexa skill on 2025-08-01, but the Wi-Fi bulbs still answer JSON commands over LAN UDP port 9080 for on/off, brightness and colour. A phone can send these directly once a bulb is on the owner's Wi-Fi, and the setup flow can re-pair bulbs to a user-owned MQTT broker. The protocol exists only in SengledTools' code. The spec should cover the UDP commands, the provisioning handshake and the MQTT topics. OTA flashing to Tasmota works only on WF863 models, and the Zigbee bulbs are unaffected. Sources: [SengledTools local control and re-pair](https://github.com/HamzaETTH/SengledTools) · [Sengled local server add-on](https://github.com/FalconFour/HA-Sengled-Local-Server-AddOn)

6. **Hörmann BiSecur Gateway** — [A] · effort M. The BiSecur Gateway is Hörmann's LAN hub for garage-door and gate operators. A community README reports official support ended around the end of 2023 or beginning of 2024, and Hörmann declined to publish the protocol. The phone app talks to it on the LAN: UDP broadcast discovery on port 4001, then hex-ASCII frames over TCP 4000 with a login token and one client at a time. bisdk/sdk already sketches the frame layout, so the spec consolidates command semantics, error codes and session handling. Caveat: frames embed gateway MACs, so every capture must be placeholdered. Sources: [bisdk/sdk protocol and frame layout](https://github.com/bisdk/sdk) · [halacs/BiSecur SDK, EOL notes](https://github.com/halacs/BiSecur)

7. **Yummly Smart Thermometer (Mastrad Meatit white-label)** — [A] · effort M. The Yummly thermometer lost its app when Whirlpool took Yummly offline in December 2024 (the RE repo gives 2024-12-18). The probe still works locally: the phone talks BLE GATT to the T1 or T3 base, completes a rotating challenge handshake, then reads TLV frames with bit-rotation obfuscation carrying core and ambient temperature, battery and signal strength. The only write-up is a single-commit repository, so a clean spec would make it durable. Mark the XW3 generation (T3 + P3) as protocol-mapped but untested, and treat the Mastrad white-label names as unconfirmed. Sources: [yummly-thermometer protocol docs](https://github.com/DavisGoglin/yummly-thermometer)

8. **LIVISI SmartHome (ex RWE / innogy) SHC 1 / SHC 2** — [A] · effort M. LIVISI SmartHome, sold since the RWE and innogy days, has a large German installed base, and the vendor website no longer resolves. The Local SmartHome API, launched around October 2022, may now be the only way to run the controllers; it survives only in openHAB, Home Assistant and Python clients. The path is plain LAN: HTTP on 8080 plus a WebSocket event stream, unencrypted, once Local SmartHome is enabled on recent firmware. It mirrors the already-specced devolo case. Main caveat: the auth flow, cloud shutdown date and any insolvency are still unsourced, and the SHC 1 and SHC 2 dialects differ. Sources: [openHAB LIVISI binding](https://www.openhab.org/addons/bindings/livisismarthome/) · [planbnet/livisi Python library](https://github.com/planbnet/livisi)

9. **Fossil Hybrid HR / Gen 6 Hybrid (Skagen, Citizen CZ, Q)** — [A] · effort L. Fossil has left the smartwatch business and is restructuring, yet Hybrid HR and Gen 6 Hybrid watches cannot be set up without a 16-byte per-watch key that only Fossil's cloud issues. The phone-direct BLE protocol, covering key-authenticated sessions, encrypted file transfer, notifications, activity sync and watch-app install, exists only in Gadgetbridge, Hybridge and small RE repos. No key-server shutdown date has been announced, which makes this time-sensitive. Gadgetbridge is AGPL, so derive facts rather than code, and describe key retrieval only as an owner exporting their own watch's key. Sources: [Gadgetbridge Fossil device page](https://gadgetbridge.org/gadgets/wearables/fossil/) · [Gadgetbridge Fossil Hybrid internals](https://gadgetbridge.org/internals/specifics/fossil-hybrid/)

10. **Sleep Number SleepIQ beds, BLE pump and base control** — [A] · effort L. Sleep Number filed Chapter 11 on 2026-06-12, and a community project already reports cloud endpoints failing and forced account migration. Phones can talk BLE GATT directly to the bed's controller for firmness, base position and lighting, but that path exists only in recent Home Assistant code. There are two protocol families: request/response MCR on older beds, and Fuzion on 360 beds, which needs bonding and authentication first. Base motion carries a pinch and entrapment hazard, so the spec must require a user present. Clean-room: the community work says MCR was found by decompiling the vendor app, so take wire-level facts only. Sources: [trooperthorn Sleep Number HA integration](https://github.com/trooperthorn/ha_int_SleepNumb) · [ha-adjustable-bed PR #579 (Fuzion, MCR)](https://github.com/kristofferR/ha-adjustable-bed/pull/579)

11. **Apple AirPort Extreme / Time Capsule / Express (ACP)** — [A] · effort L. Apple discontinued the AirPort Extreme and Time Capsule in April 2018, and the management protocol, ACP on TCP 5009, is known only from two community codebases, one archived in 2022. The local path is fully cloud-free: property get/set, reboot, feature detection and logs, with SRP authentication and an encrypted session. A spec would let the app stand in for Apple's ageing AirPort Utility on any platform. Effort is large because of the property encoding and catalogue. The spec must recommend SRP over the weak legacy auth and leave out the firmware decryption and flashing material both repos contain. Sources: [node-acp (port 5009, SRP)](https://github.com/samuelthomas2774/node-acp) · [airpyrt-tools Python ACP client](https://github.com/x56/airpyrt-tools)

12. **Philips Wi-Fi air purifiers and humidifiers** — [B] · effort M. A large installed base of Philips purifiers and humidifiers, phone-direct, with a local protocol that exists only in client code, and firmware updates that are removing local access on some models. The local path is encrypted CoAP over UDP to the unit with no account, as implemented by aioairctrl; the oldest units use HTTP or plain CoAP. Scope the first spec to the encrypted-CoAP generation, list the FUSION cloud-relay models as parked, and record which firmware still allows local control. Port 5683 and AES-128-CBC still need confirming from code. Sources: [aioairctrl encrypted CoAP library](https://github.com/betaboon/aioairctrl) · [philips-airpurifier-coap models and caveat](https://github.com/kongo09/philips-airpurifier-coap)

13. **GE Cync / C by GE lights, plugs and switches** — [B] · effort L. GE Cync has a very large US installed base, and GE Lighting has stopped making the original C by GE bulbs. The phone joins the Telink BLE mesh directly with AES-encrypted opcodes, as the vendor app does, but the protocol is split across four client code bases. Mesh credentials must be exported from the Cync cloud once, so the spec should say what happens when that export is gone. Wi-Fi models need a LAN server and DNS override; keep them separate. A shared Telink-mesh spec could cover AwoX/EGLO. Sources: [cync2mqtt Telink BLE mesh](https://github.com/juanboro/cync2mqtt) · [cync-lan cloud impersonation (TLS)](https://github.com/baudneo/cync-lan)

14. **EcoFlow power stations and home-energy devices (BLE)** — [C] · effort L. EcoFlow's app demands a server login even over Bluetooth, and the main reverse-engineering repo, ef-ble-reverse, was archived on 2026-09-16, so a written spec would preserve a protocol that now lives only in code. The phone talks to the unit directly: an ECDH key exchange, then AES-128-encrypted frames carrying protobuf (V3 devices) or a legacy binary payload (V2, such as Wave 2). After a one-time account User ID lookup it runs fully offline. Caveat: that repo derived its schemas by decompiling the app, so field meanings must be restated in the spec's own words. Sources: [ef-ble-reverse protocol RE](https://github.com/rabits/ef-ble-reverse) · [ESP32-Ecoflow-BLE handshake notes](https://github.com/lollokara/ESP32-Ecoflow-BLE)

15. **Drobo NAS status daemon (FS / 5N / 5N2 / B810n)** — [A] · effort S. Drobo's parent was liquidated in 2023 and its Dashboard software is unsupported, but owners still run BeyondRAID arrays whose drive health is visible only through an undocumented status socket. On TCP port 5000 the NAS pushes a 16-byte 'DRINASD' header and an XML status document every 10-20 seconds, with no authentication, so a phone on the LAN can read it directly. Community notes and a wiki page cover the format, making this a small spec. It should stay read-only, handle the three header-magic variants, and paraphrase rather than copy the daemon's internal command names. Sources: [drobo-nas-protocol notes](https://github.com/jerimiah797/drobo-nas-protocol) · [DroboPorts wiki: NASD XML format](https://github.com/droboports/droboports.github.io/wiki/NASD-XML-format)

16. **Kano Harry Potter Coding Kit Wand** — [A] · effort S. Kano Computing went into administration on 2023-06-06, leaving the Harry Potter wand with an insolvent vendor. The wand talks BLE GATT straight to the phone with no cloud: three custom services (info, IO, sensor) share a 64a7… UUID base, alongside a Nordic DFU service. The map is confirmed on a Hackaday log, but the button, vibration, LED and 9-axis stream semantics are scattered across hobby clients. A small spec makes the wand a gesture-input device for the app. Spell recognition runs on the host, so it stays out of scope. Sources: [Kano Wand Hack GATT map](https://hackaday.io/project/161832-kano-wand-hack) · [kano_wand Python client](https://github.com/GammaGames/kano_wand)

17. **TiVo DVRs and Minis (Series 3+): network remote, Mind RPC** — [A] · effort S. TiVo left hardware manufacturing on 2025-10-01 and now sells only monthly service, but a large fleet of Series 3 and later boxes remains. Once the owner enables Network Remote Control, each box accepts an unauthenticated text remote on TCP 31339 and announces itself over mDNS or legacy port-2190 beacons. That protocol survives only as an old forum post and scattered clients, so a small phone-direct spec is quick to write. Mind RPC on Series 4+ can follow later; it needs a TiVo-issued certificate, which must never be shipped or quoted. Sources: [tivoremote network remote client](https://github.com/wmcbrine/tivoremote) · [kmttg wiki: remote control RPC](https://sourceforge.net/p/kmttg/wiki/remote_control/)

18. **Hot Wheels id Smart Track Race Portal (FXB53)** — [A] · effort S. Mattel's Hot Wheels id app was discontinued on 2024-01-01 according to the community project, leaving the Race Portal (FXB53) without official software. The portal is phone-direct: it advertises HWiD over BLE and exposes three services for authentication, data and control, then reports each car's NFC UID, serial and NDEF records along with float32 speed and lap events. One small repository already has a PROTOCOL.md, so a clean spec mainly adds durability. Cite the retirement date as community-sourced, and describe the car-ID structure without copying Mattel's ID tables. Sources: [hotwheels-portal BLE protocol](https://github.com/mtxmiller/hotwheels-portal)

19. **IKEA TRÅDFRI Gateway E1526 (CoAP over DTLS-PSK)** — [A] · effort M. IKEA stopped updating the TRÅDFRI gateway in July 2024 in favour of DIRIGERA, leaving a very widely owned Zigbee gateway frozen. It works fully locally: coaps on UDP 5684, a PSK obtained from the label's security code, and GET/PUT on LwM2M/IPSO resources for devices, groups and scenes. A good prose reference exists, so the value is consolidation: fixtures, the pairing state machine and the object-ID tables, in the same shape as osram-lightify-gateway. The main risk is the phone side, since Flutter/Dart DTLS 1.2 PSK support is thin. Sources: [TRÅDFRI CoAP docs (glenndehaan)](https://github.com/glenndehaan/ikea-tradfri-coap-docs) · [Debugging CoAPS with TRÅDFRI gateway](https://github.com/Jan21493/Debugging-COAPS-with-IKEA-Tradfri-gateway)

20. **Oura Ring Gen3 and Ring 4, BLE sync protocol** — [A] · effort M. Oura gates detailed data behind a paid membership, yet the ring itself speaks BLE GATT directly to the phone. After an AES-128 nonce exchange under a 16-byte per-ring key, a client can read battery, live heart rate, SpO2 and the history-event stream with no Oura account. Public RE from 2025-26 is spread across open_oura, its forks and ringverse, so a clean-room consolidation would help owners of used rings or lapsed memberships. Carry only wire facts, no app internals or scoring models, and label health fields non-clinical. Sources: [open_oura Rust toolkit](https://github.com/Th0rgal/open_oura) · [ringverse Oura Ring 4 BLE](https://github.com/ringverse/protocol/blob/main/oura/BLE.md)

21. **Echelon Connect bikes and Stride (pre-July-2025 firmware)** — [A] · effort M · *July list*. Echelon's July 2025 firmware made bikes wait for a server authentication challenge before streaming metrics over BLE, which ended offline use and broke third-party apps. Bikes and treadmills still on older firmware speak a plain phone-direct BLE profile for cadence, resistance, power and speed, already public in QZ's GPL drivers. A spec keeps un-updated and second-hand machines usable without a subscription. Because of DMCA §1201, it must cover only the pre-update profile and say nothing about meeting or bypassing the new challenge. Sources: [QZ issue #62: Echelon BLE log](https://github.com/cagnulein/qdomyos-zwift/issues/62) · [QZ Equipment Compatibility wiki](https://github.com/cagnulein/qdomyos-zwift/wiki/Equipment-Compatibility)

22. **Insteon Hub 2245-222 (v2) / 2242-222 (v1)** — [A] · effort M · *July list*. Insteon's servers went down without notice in mid-April 2022, but hubs kept running offline with their local API intact. Hub v2 (2245) takes raw PLM commands over HTTP on port 25105 with Basic auth from the hub label and returns replies through a 200-character circular buffer that must be polled about twice a second; Hub v1 (2242) uses a different transport on port 9761. The repo already has an unvalidated research note. Link the vendor PLM guide rather than restating it, spec the Hub v2 wrapper and buffer semantics, and placeholder hub credentials. Sources: [KRKeegan Hub2 technical inspection](https://krkeegan.com/technical-inspection-of-insteon-hub2-2245-222/) · [Home Assistant Insteon integration](https://www.home-assistant.io/integrations/insteon/)

23. **Hasbro Furby Connect (2016)** — [A] · effort M. Furby Connect lost its companion app when Hasbro dropped support (quoted from the PyFluff README; no date given). Control is phone-direct over BLE GATT: a Nordic SoC fronts the GeneralPlus main MCU and accepts commands for actions, antenna LED colour, mood and LCD backlight, sends joystick, tickle and accelerometer notifications, and takes DLC uploads for eye animations and audio. bluefluff already has a doc folder, so the work is consolidating it with the modern Python port into one spec. Document the DLC container format only, never the content of Hasbro's own DLC files. Sources: [bluefluff protocol docs](https://github.com/Jeija/bluefluff) · [PyFluff Python control library](https://github.com/martinwoodward/PyFluff)

24. **Nissan Leaf (ZE0 / AZE0 / ZE1) battery data over OBD-II** — [A] · effort M. Nissan shut down NissanConnect EV in the UK and Europe on 30 March 2026 for pre-2019 Leafs, so owners there have lost the cloud telematics path. Battery state of charge, state of health and capacity can still be read locally: a phone talks to a plug-in BLE ELM327-class OBD-II adapter and sends diagnostic polls such as the LBC query 0x79B with its response on 0x7BB. Public CAN spreadsheets and DBC files already exist, so the spec's value is a clean decode write-up on the repo's OBD, UDS and ISO-TP layers. Keep it strictly read-only, with separate tables for each generation. Sources: [Leaf CAN spreadsheet and DBCs](https://github.com/dalathegreat/leaf_can_bus_messages) · [nissan-leaf-obd-ble integration](https://github.com/pbutterworth/nissan-leaf-obd-ble)

25. **Eye-Fi Wi-Fi SD cards (X2 and earlier; Mobi / Mobi Pro)** — [A] · effort M. Eye-Fi dropped support for X2 and earlier cards after 16 September 2016, and Keenai, the Eye-Fi Cloud successor, closed on 1 December 2018. The cards still work locally: they push photos over a SOAP upload protocol to a receiver on the LAN on TCP 59278, and Mobi Pro also has a direct peer-to-peer mode. A phone app can take the receiver's place. The spec needs two parts: the receiver-side session with the credential and nonce exchange (which differs between X2 and Mobi), and the hidden-file configuration channel on the card. Describe the hash inputs in prose and never copy SOAP bodies from the servers. Sources: [eyefiserver2 Python server](https://github.com/dgrant/eyefiserver2) · [node-eyefimobiserver Mobi server](https://github.com/michaelbrandt/node-eyefimobiserver)

26. **Slingbox place-shifters (240/350/500/M1/M2/Solo/Pro/Pro-HD)** — [A] · effort L. Sling Media shut its servers down on 2022-11-09, and the SlingPlayer app went with them. The boxes still accept direct LAN connections: Slinger re-implements the client, sends IR remote codes, sets resolution and re-serves the video. Its README lists the IR codes and resolutions, but the handshake, auth and stream framing exist only in code. A spec would let a phone app talk to the box directly. The open questions are recovering the admin password after the shutdown and several chipset generations. Stream obfuscation touches pay-TV content, so cipher details need a DMCA 1201 review first. Sources: [Slinger local Slingbox server](https://github.com/GerryDazoo/Slinger) · [Wikipedia: Slingbox](https://en.wikipedia.org/wiki/Slingbox)

27. **Anki / DDL Cozmo robot** — [A] · effort L. Cozmo's behaviour engine runs on the phone, and the app comes from Digital Dream Labs, which the Pennsylvania Attorney General sued in 2024. The phone joins the robot's own access point and speaks a UDP protocol on port 5551 with selective-repeat ARQ framing. pycozmo's docs describe the transport clearly, but every message definition sits only in generated code, so the message layer is code-only. A first spec should cover transport, handshake and the core drive, lift, head, display and audio messages. Do not draw on cozmo-stack, which was built from decompiled vendor material. Sources: [pycozmo protocol doc](https://github.com/zayfod/pycozmo/blob/master/docs/protocol.md) · [pycozmo Python client](https://github.com/zayfod/pycozmo)

## Handle with care

A few rules cut across the tables. The verification pass raised each of them
on more than one device.

- **Bluetooth Classic has no home in the schema yet.** `device.protocol` is
  `ble`, `wifi`, `lan`, `zigbee`, `zwave`, `obd2`, `uart` or `can`, so an
  RFCOMM/SPP device has nowhere to go. That blocks the Bose QuietComfort, Sony
  and Galaxy Buds control protocols, Apple's AAP, and the Parrot Zik, Jambox
  and Nuraphone research notes. Propose the value in
  [spec evolution](../contributing/spec-evolution.md) before writing those
  specs. The mobile app would also need the transport, and iOS cannot open SPP
  at all.
- **One-time key exports.** VanMoof, Fossil Hybrid HR, Oura, GE Cync and
  EcoFlow need a per-device key or account identifier that only the vendor
  cloud ever issued. Tapo/KLAP needs the cloud account's credentials, which
  the device learned during a cloud-mediated setup. Spec the key's role, format and
  where the owner can retrieve their own key. Never commit a key, and say
  plainly what happens once the retrieval service is gone.
- **Things that move, heat or are worn by an infant.** For e-bikes, boards,
  EV chargers, beds, pressure cookers, grills and baby monitors, keep the spec
  to what the vendor app itself did. Leave out speed-limit, region and
  charge-current overrides beyond the installer's rating, and any
  alarm-replacement behaviour. The VanMoof, Boosted, JuiceBox, Sleep Number,
  Instant Pot and Owlet rows each carry the specific caveat.
- **Firmware that has already locked the door.** For Echelon, spec *only* the
  pre-July-2025 BLE profile, which is already public. The newer server
  challenge, and any way around it, is out of scope: a working jailbreak exists
  but cannot legally be released
  ([404 Media](https://www.404media.co/developer-unlocks-newly-enshittified-echelon-exercise-bikes-but-cant-legally-release-his-software/)).
- **Sources derived from decompiled apps.** Several public projects say they
  were built by decompiling the vendor app. Examples: the EcoFlow BLE work,
  the Sleep Number MCR protocol, one Cozmo stack, and a Joule project that
  republished `.proto` files. Take wire-level facts only, restate them in your
  own words, and never copy schema files, constants or class names. See
  [Clean-room Rules](../CLEANROOM_RULES.md).

## Link, don't spec

Real local control, but the protocol is already written down, by the vendor or
in a clean community document. A fresh spec would compete with it rather than
rescue anything: the pywemo situation the README describes. The useful

one of these only if the existing document is at risk: a dead vendor's
domain, or a single fragile repository. The Neurio note in the graduation

## Corrections this survey found in existing pages

- **`research-notes/thermostat-cloud-locked-duds.md`** rejects the Mitsubishi
  Kumo Cloud adapters (PAC-USWHS002/003) as cloud-only. `pykumo` and the Kumo
  Home Assistant integration drive them over a local API. The Kumo row above
  has the details.
- **[Candidate Devices](device-candidates.md), Anova Generation 2**: the
  Precision Cooker **Mini** does not use the Nano's COBS + protobuf framing. It
  has its own BLE service with JSON payloads Base64-encoded
  ([vendor docs](https://developer.anovaculinary.com/docs/devices/mini/overview)).
  In Generation 3, the Wi-Fi WebSocket is a *cloud* endpoint, not a LAN one
  ([bogd/anova-oven-api](https://github.com/bogd/anova-oven-api/blob/main/docs/README.md)),
  and the `awgneo/anova-homeassistant` repository that page cites no longer
  resolves.
